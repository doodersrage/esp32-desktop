# esp32-desktop

Native Qt 6 workbench and simulator for ESP32 boards, for Linux: Arch, Debian, Ubuntu and Fedora (developed on KDE Plasma), with macOS and Windows to follow (phase 6). Desktop companion to esp32bench.dev.

The plan is in `docs/PLAN.md`. Read it before any design work. It is the source of truth for scope, decisions and phase order.

## Current state

Phases 1 and 3 are done (checked on Plasma, `docs/hardware-notes.md`; the library sweep, `tests/library/sweep.py`, is in `docs/library-sweep.md`: every library build succeeds, and 222 of 227 simulated builds print their expected output: all but the Bluetooth sketch, on every board); phase 2 is feature complete; erase, whole-flash restore, and reading and writing through a PL2303 UART bridge were checked on the C3; the automatic DTR/RTS reset of auto-reset boards is still untried. Phase 4: on lcgamboa's library (ESP32, S3 and C3) a simulation bridges the GPIOs its build uses (from the library's `pins`), the daemon reports them (`sim.pins`, batched every 50 ms, with each pin's `rate` (how fast it toggles and how much of the time it is high, over the last two simulated seconds, `esp32bench_sim::trace::Trace::rate`) when it changes) and drives them (`sim.setPin`), and a Pins dock shows them, with their rates. Each change also goes into a signal trace (`esp32bench-sim::trace`): the host stamps it with QEMU's virtual clock (`qemu_clock_get_ns`), the daemon keeps the latest million edges of the last eight sessions per connection and streams them (`sim.trace`), and `sim.traceSave` or `sim run --trace <file>` writes them as VCD for PulseView or GTKWave. ## Decisions that are settled

Do not reopen these without the owner asking. Each has its reasoning in `docs/PLAN.md`.

- Qt 6 Widgets in C++ for the UI. Not QML, not GTK, not a webview.
- Rust core in a separate process. The UI never links Rust code.
- JSON-RPC over a Unix socket between UI and core.
- `arduino-cli` and `idf.py` are both first-class build systems.
- GPLv2-or-later. QEMU is GPLv2, so GPLv3 is ruled out.
- lcgamboa's QEMU fork for the simulator, pinned to a commit and built from source. GPIO and I2C go through its library build in a per-session host process.
- The app name is `esp32bench` (CLI, crates, data and runtime directories, `ESP32BENCH_*` variables). The repo stays `esp32-desktop`.
- Supported platforms for v1 are Arch, Debian 13, Ubuntu 24.04 and 26.04 LTS, and Fedora 44 and 45, on any desktop (the owner widened this from Arch with Plasma on 2026-11-19). Each release has packages for all of them (`.pkg.tar.zst`, `.deb`, `.rpm`), built and install-tested by `.github/workflows/packages.yml`. macOS and Windows are target platforms too (the owner added them on 2026-11-19, phase 6, `docs/platforms.md`): `.github/workflows/macos.yml` and `windows.yml` build a `.dmg` (`packaging/macos/`) and a `.zip` and Inno Setup installer (`packaging/windows/`) with the simulator prebuilt inside, and smoke-test them (the core over its socket or named pipe, firmware on all three chips through the bundled simulator, pins both ways, and building and simulating a library project with the app's own arduino-cli, and on Windows a local ESP-IDF project); released since 0.1.7 (`packages.yml` calls both workflows on a tag), and real boards there are unchecked. Platform differences live in `esp32bench_distro::dirs` (data folders), `esp32bench_rpc::transport` (named pipes on Windows) and `esp32bench_sim::link` (loopback TCP for QEMU's links on Windows); the core must keep compiling for all three (`cargo clippy --target aarch64-apple-darwin` and `x86_64-pc-windows-gnu` check it without the systems).
- The serial monitor is a plain text view (`QPlainTextEdit`), not QTermWidget.
- On macOS and Windows the app ships the simulator prebuilt: the release builds the patched fork's library there (statically on Windows) and packages it; Linux keeps building it from source in the setup step (decided 2026-11-20 from phase 6's spike, `docs/platforms.md`).
- Virtual parts are placed in the app first, saved per project and board on this computer, in a versioned circuit format the shared manifest may adopt later.
- Simulations get a simulated Wi-Fi network that reaches nothing (restricted user-mode networking; only the firmware's port 80 forwarded to loopback).
- Part models are a JSON description plus a Rhai script, built into the program, and run in `esp32bench-qemu-host` (`docs/parts.md`).

## Working rules

1. **Core first.** Every feature lands in the core with a JSON-RPC method and a test before any UI is written for it. The CLI must be able to do everything the UI can.
2. **No logic in the UI.** The UI renders state and sends requests. Serial parsing, build orchestration, QEMU control and file formats belong in the core.
3. **Schema changes are shared changes.** Files in `schema/` are consumed by the esp32bench.dev site. Never make a breaking change without bumping the schema version and noting it in the commit message.
4. **Nothing runs without consent.** Anything opened from an `esp32bench://` link or a downloaded project is untrusted. The app must ask before building or flashing it. Do not add a path that skips the prompt.
5. **No root.** Device access comes from the udev rule and the `uucp` group. Never add code that calls `sudo` or `pkexec`.
6. **Simulator claims stay honest.** The simulator is firmware-level. Do not describe an unsupported peripheral or board as working. Boards outside ESP32, S3 and C3 are workbench-only.
7. **Translatable strings.** Every user-visible string in the UI goes through `tr()`.
8. **Pin versions.** QEMU builds, IDF versions and Arduino core versions used in tests are pinned in the repo, never "latest".
9. **Stay in v1 scope.** No built-in code editor, analog simulation, or Flatpak. Raise it with the owner instead of building it.
